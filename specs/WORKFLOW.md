# RainbowFish 开发工作流

这份文档是处理需求、缺陷和交付的入口。开始前先看当前仓库、项目规则和已有 Feature 记录，再按改动的性质选流程。可复制的记录格式见 [workflow-templates.md](./workflow-templates.md)。

RainbowFish 要同时提供多模态共享记忆、自己的 Agent，以及供 Codex、Claude Code、pi 等宿主使用的接入能力。工作流要覆盖这些边界，但每次只验证实际受影响的部分。当前已建立 Git 与 GitHub 仓库，尚无应用代码、测试脚本或 CI；后续以现场为准，不预设命令、PR、部署或干净的工作区。

## 先判断走哪条路

| 情况 | 路径 | 记录 |
| --- | --- | --- |
| 已有行为出错 | Bugfix：Reproduce → Root Cause → Fix Plan → Impl → Regression Verify → Ship | 一份 bugfix.md |
| 小范围、低风险、边界清楚的增强或调整 | Quick：Intent → Quick Spec → Impl → Verify → Ship → Iterate | 一份 quick-spec.md，含简短 Review 和交付记录 |
| 新模块、跨层能力、重要数据或权限变更、较高风险 | Full：Intent → Spec → Plan → Tasks → Impl → Verify → Review → Ship → Observe → Iterate | intent.md、spec.md、plan.md、tasks.md、verify.md、review.md、summary.md |

记录放在根目录的 `specs/<编号-名称>/`；编号按实际 Feature 递增，名称写清主题。只有具体工作需要记录时才建目录，不为尚未确定的首版设想预建 Feature。缺陷和 Quick 各保留一份记录，随着进展在原文补齐，不拆成多份阶段报告。

讨论、调查、写 Spec 与实施代码是不同阶段。只获得讨论或文档授权时，交付相应结论或文档；进入代码阶段需要已有授权覆盖。一次授权已覆盖后续阶段时顺序推进，不逐阶段重复询问，也不越过尚未授权的范围。

## Full Feature

顺序固定为 Spec → Plan → Tasks。Spec 说明可观察行为，Plan 说明方案及边界，Tasks 才把 Plan 拆成可执行工作。多 Plan 时使用 plan-01.md、plan-02.md 等，仍只用一份 tasks.md，并标清每个任务属于哪个 Plan。每次只执行已授权的 Plan；完成且验收一个 Plan 可以形成一次交付，不代表自动获得提交权限。

| 阶段 | 输入 | 输出 | Agent 动作 | 人类关注 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- | --- |
| Intent | 用户场景、问题和已有证据 | 简短 intent.md | 写清用户、目标、成功表现及本次不做的事 | 问题和值得解决的范围 | 目标可判断，边界没有明显歧义 |
| Spec | Intent、现有行为和真实使用场景 | spec.md | 描述行为、异常、权限及验收条件；区分事实和假设 | 行为是否符合预期，首版范围是否合适 | 关键行为能被验收，待定事项已显式标出 |
| Plan | Spec、现有代码或技术事实 | plan.md，必要时分多个 Plan | 调查真实结构，提出数据流、接口、状态和关键取舍；按风险规划验证 | 方案是否足够简单，权限、事务、并发和失败路径是否清楚 | 方案覆盖 Spec，阶段边界明确 |
| Tasks | 已确定的 Plan | 统一 tasks.md | 按依赖拆成范围可控、完成条件可查的任务，关联 Plan | 先后顺序与每步的可审查性 | 每个任务能定位修改范围和验证方式 |
| Impl | 已授权的 Plan、Tasks、现有代码 | 实际改动与任务进度 | 先查原因和既有实现，再逐项修改；完成一项做必要的定向检查 | 实际行为和计划偏差 | 已授权范围的任务完成，偏差已记录或重新决策 |
| Verify | Spec 验收条件、改动、任务检查证据 | verify.md | 按本次风险验证，复用仍有效的既有证据，记下未执行项与证明边界 | 关键场景是否真能工作，哪些结论仍未证实 | 验收所需证据足够；剩余风险明示 |
| Review | Spec、Plan、Diff、Verify | review.md | 对照 Spec 和 Diff 查遗漏、无关改动及高风险路径，处理发现 | 取舍和遗留问题是否可接受 | 审查问题已处理，或有明确留待后续的理由 |
| Ship | 已审查的结果与当前仓库状态 | 简短 summary.md 和明确交付状态 | 说明改了什么、验证到哪、能否使用；按已有授权处理提交或发布 | 是否验收、是否允许提交或发布 | 状态写实，不把“完成代码”等同于“已发布” |
| Observe | 已在真实环境使用的结果 | 必要时补充观察记录 | 看错误、耗时、资源、Agent 行为和用户反馈中与本次有关的信号 | 实际使用是否达到目标 | 有可判断的使用结果，或明确尚无观察条件 |
| Iterate | 观察结果或新需求 | 新的 Intent、Quick 记录或 Bugfix 记录 | 将新的问题重新定界，不无限追加到旧 Feature | 新问题的优先级和范围 | 选好下一轮流程 |

## Quick 与 Bugfix

Quick Spec 在一份 quick-spec.md 内合并 Requirement、Design、Tasks。写出场景、预期行为、最小改法、实施步骤、验证和交付状态即可。小改动的 Review 可在同一份记录中对照需求与 Diff 写几句；若碰到原先未知的跨层风险，先重新定界，再决定是否升级 Full。

Bugfix 在一份 bugfix.md 中依次记录 Reproduce、Root Cause、Fix Plan、Impl、Regression Verify、Ship。先写触发条件、预期与实际结果，说明是否稳定复现；根因要有代码或运行证据，不能只修表面现象。修复计划交代影响范围和回归风险，验证覆盖原故障与必要的相邻正常路径。无法运行的检查照实记录，不能写成通过。

## 验证与审查

验证按改动风险选择，不为每次修改做全量测试，也不为凑数量添加只复述实现的测试。仓库有脚本时读取实际脚本再执行；没有脚本时记录可执行的手工步骤或“未执行”及原因。其他 Agent 已提供清楚、对应同一改动状态的验证证据时直接复用；出现新改动、失败或未覆盖风险才重跑相关检查。后台进程只有演示确需保留时才继续运行，用完及时关闭。

按改动涉及的边界选择场景：

- 桌面与打包：涉及 Electron 主进程、preload、界面或原生依赖时，检查对应交互；涉及分发时验证 Windows 打包产物的启动和关键路径。
- Agent 行为：用实际任务场景或可复现的场景输入，检查任务完成情况、工具选择、参数与结果处理、循环检测和停止条件、错误恢复、权限及状态变化，而非只比较模型输出字符串。
- Agent 效果与成本：按受影响的风险选择指标；评估任务效果时记录成功数、总数与成功条件，涉及性能或上下文策略时记录延迟、Token 用量和上下文增长。固定用例、模型配置与重复次数写入验证记录；未执行的项标明原因，不要求每次全量 Eval。
- 记忆：检查写入、召回、来源定位、纠错和旧版本边界；不要把候选推断当用户确认事实。
- 跨 Agent：涉及接入时检查具体宿主会话关联、发现、读取范围和更新后再次读取的行为；只覆盖本次实际接入的宿主。
- 多模态：涉及图片、音频或视频时检查原始材料仍可回读，证据位置能定位到对应区域或片段；摘要不能替代原证据。

Review 先对照 Spec 的验收条件和本次 Diff，再看错误路径、权限、事务、并发、无关改动和过度抽象。完整 Feature 的 review.md 记录结论与待处理项；风险需要独立审查时由 Astra max 执行。Quick 或 Bugfix 的小改动可在原记录中写 Review，不另造文件。

## 交付状态与权限

Ship 时分别说明：**可用**（可在什么环境使用）、**已验收**（谁根据什么证据接受）、**未提交／已提交**（仅在仓库有 Git 时）、**已发布**（实际分发或部署完成）。这些状态不能互相代替；未发生的动作就写未发生，不伪造干净工作区或测试通过。

提交前必须得到用户对本次提交的明确同意；无论单 Plan 还是多 Plan 的一个已验收 Plan，都只是允许的交付粒度，不是提交授权。禁止自行推送。PR、CI、预览和部署仅在项目确有对应环境且任务需要时使用。
