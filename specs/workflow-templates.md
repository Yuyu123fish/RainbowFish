# 工作记录模板

按 [WORKFLOW.md](./WORKFLOW.md) 选流程，再把需要的模板复制到根目录的 `specs/<编号-名称>/`。保留本次真正需要的栏目，删去不适用的提示；不要为填满模板编造行为、命令或验证结果。所有“已验证”都要有实际执行的步骤、结果和适用范围；未执行就写明原因与因此无法证明的事。

完整 Feature 用下面七份文件。若一个 Feature 分成多个 Plan，把 plan.md 改成 plan-01.md、plan-02.md 等；tasks.md 始终只有一份，并标明任务所属 Plan。先完成 Plan，再拆 Tasks。

## Full：intent.md

~~~markdown
# Intent：<主题>

## 要解决的问题
<谁在什么场景遇到什么困难；已有事实与猜测分开写。>

## 本次目标
<完成后可观察到的变化。>

## 成功标准
- <可判断的结果>

## 本次不做
- <明确排除的范围；没有则删除本栏>
~~~

## Full：spec.md

~~~markdown
# Spec：<主题>

## 场景与现状
<用户如何使用；现有行为以已核实的事实为准。>

## 预期行为
- <场景／触发条件 → 系统行为>

## 边界
- <权限、错误、冲突、删除或多模态证据等本次相关情况>

## 验收条件
- [ ] <从用户可见行为判断是否完成>

## 约束与待定
<已有决定、尚未确认的选择；没有则删除本栏。>
~~~

## Full：plan.md（或 plan-01.md 等）

~~~markdown
# Plan：<主题或阶段>

## 对应范围
<对应 Spec 的哪些验收条件；本 Plan 完成到哪里。>

## 现状依据
<已检查的代码、接口、数据或运行行为；新项目则写当前确实存在的基础。>

## 实现方案
<关键组件、数据流、接口或状态变化。只写本次需要的设计。>

## 关键边界与取舍
<按需说明权限、事务、并发、错误处理、兼容与替代方案。>

## 风险与验证
<哪些地方容易出错；准备通过什么实际场景或检查验证。>

## 阶段交付
<本 Plan 的可审查结果、依赖和暂不进入的后续阶段。>
~~~

## Full：tasks.md

多 Plan 时仍在本文件持续维护，不为每个 Plan 建一份 Tasks。任务完成条件要能通过产物或行为核对，不用“完成整个功能”充当一个任务。

~~~markdown
# Tasks：<主题>

## T1：<具体结果>
- 所属 Plan：<plan.md 或 plan-01.md>
- 目标与范围：<这一步做什么、涉及哪里>
- 依赖：<前置任务；没有则写无>
- 完成条件：<可核对的产物或行为>
- 定向验证：<实际执行后补步骤、结果和证据；未执行说明原因>
- 状态：待做

## T2：<具体结果>
- 所属 Plan：
- 目标与范围：
- 依赖：
- 完成条件：
- 定向验证：
- 状态：待做
~~~

## Full：verify.md

验证项目按本次风险选择。若其他 Agent 已提供对应当前改动的清楚证据，记录其来源与适用范围；出现新改动或新风险时再做相关检查。

~~~markdown
# Verify：<主题>

## 本次验证范围
<对应 Spec 哪些验收条件、哪个 Plan、哪个改动状态。>

| 场景或检查 | 执行方式 | 结果 | 证据与证明边界 |
| --- | --- | --- | --- |
| <实际检查项> | <真实命令或手工步骤> | <通过／失败／未执行> | <输出、观察结果、环境和范围> |

## 未执行或未覆盖
- <项目及原因；因此仍无法证明什么。没有则删除本栏。>

## 结论
<哪些行为已被证明，哪些风险需要继续处理。>
~~~

## Full：review.md

~~~markdown
# Review：<主题>

## 对照范围
<本次 Spec 验收条件、Plan 和实际 Diff。>

## 发现与处理
- <遗漏、无关改动或高风险路径；对应位置与处理结果>

## 审查结论
<可以进入交付／仍需修复什么；注明审查者和证据范围。>
~~~

## Full：summary.md

只记录能帮助下一轮理解本次结果的事实，不写日报。

~~~markdown
# Summary：<主题>

## 交付结果
<实现了什么；哪些目标仍未完成。>

## 关键取舍
<会影响后续开发的决定；没有则删除本栏。>

## 验证与审查
<引用 verify.md、review.md 的结论和剩余边界。>

## 当前状态
- 可用：<环境与条件，或尚不可用>
- 验收：<已验收及依据，或未验收>
- Git 提交：<未提交／已提交；无 Git 时写不适用>
- 发布：<未发布／已发布及去向>

## 后续
<尚需处理的问题；没有则删除本栏。>
~~~

## Quick：quick-spec.md

一份文件贯穿 Intent、Requirement、Design、Tasks、Verify、Review 和 Ship。实现前先写清需求与最小方案，实施后在原文补实际记录。

~~~markdown
# Quick Spec：<主题>

## Intent / Requirement
<谁在什么场景需要什么变化；怎样算完成。>

## Design
<现状依据、最小改法与影响范围。>

## Tasks
- [ ] <有明确结果的小步骤>

## Verify
<实际执行的步骤、结果和范围。未执行时说明原因及无法证明的部分。>

## Review
<对照需求和 Diff 的结论；发现与处理。>

## Ship
<可用、验收、提交、发布分别是什么状态；只写实际发生的事。>
~~~

## Bugfix：bugfix.md

先找到原因，再修改。无法稳定复现时保留复现条件和证据缺口，不能把猜测写成根因。

~~~markdown
# Bugfix：<现象>

## Reproduce
- 触发条件与步骤：
- 预期：
- 实际：
- 是否稳定复现及证据：

## Root Cause
<导致现象的原因、代码或运行证据；未查明则写待查。>

## Fix Plan
<如何针对根因修复、影响范围、可能的回归点。>

## Impl
<实际改动及与计划的偏差。>

## Regression Verify
- 原故障：<步骤、结果、证据或未执行原因>
- 相邻正常路径：<按风险选择的检查、结果及范围>
- 尚未证明：<没有则删除本行>

## Review
<对照修复目标与 Diff 的简短结论；高风险时记录独立审查结果。>

## Ship
<可用、验收、提交、发布分别是什么状态；只写实际发生的事。>
~~~
